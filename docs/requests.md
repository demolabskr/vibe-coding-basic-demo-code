# 요청 기록

이 사이트는 아래 요청을 차례로 AI 코딩 에이전트에게 맡겨 만들었다. 큰 일을 바탕, 판매, 마무리 세 덩어리, 열 개 요청으로 쪼갰고, 요청마다 목적, 끝나는 기준, 하지 말 것, 확인 방법 네 줄을 적었다.

요청 하나가 끝나 확인을 통과할 때마다 커밋하고 태그를 붙였다. `git switch --detach step-03`처럼 태그로 옮기면 그 단계의 사이트를 그대로 볼 수 있다.

새 대화를 열 때는 [기획 메모](plan-memo.md)를 먼저 붙이고 요청을 보냈다. 규칙 파일([AGENTS.md](../AGENTS.md))은 에이전트가 매번 스스로 읽는다.

## 0. 기획 문서 `step-00`

```text
목적: 기획 메모를 바탕으로 PRD와 화면 흐름(와이어프레임)을 문서로 만든다.
끝나는 기준: docs/에 plan-memo.md, PRD.md, wireframe.md가 있고, 첫 판 기능이 여섯 가지다.
하지 말 것: 코드를 만들지 않는다. 쿠폰과 후기를 넣지 않는다.
확인 방법: PRD의 기능 표와 기획 메모의 "어디까지" 문장을 나란히 읽는다.
```

## 바탕

### 1. 뼈대와 규칙 파일 `step-01`

```text
목적: Django 프로젝트 뼈대를 만들고 규칙 파일, README, .gitignore, .env.example을 둔다.
끝나는 기준: 개발 서버를 켜면 첫 화면이 열린다. 비밀 키는 .env에서 읽는다.
하지 말 것: 다른 프레임워크를 제안하지 않는다. .env를 저장소에 올리지 않는다.
확인 방법: 서버를 켜고 http://127.0.0.1:8000/ 을 연다. git status에 .env가 보이지 않는다.
```

### 2. 콘텐츠 표와 관리자 화면 등록 `step-02`

```text
목적: 콘텐츠 표(Content)를 만들고 관리자 화면에서 등록하게 한다.
끝나는 기준: 관리자 화면에서 표지와 판매 파일을 올려 콘텐츠를 등록하고 숨길 수 있다.
하지 말 것: 판매 파일을 공개 주소가 있는 media/에 두지 않는다.
확인 방법: 관리자로 로그인해 콘텐츠 하나를 올리고, 판매 파일이 private/ 아래에 저장되는지 본다.
```

### 3. 목록 페이지 `step-03`

```text
목적: 공개된 콘텐츠를 카드로 보여 주는 목록 페이지를 만든다.
끝나는 기준: /contents/ 에 공개 콘텐츠만 보이고, 종류별로 거를 수 있다. 휴대폰 폭에서 한 줄에 한 장.
하지 말 것: CSS 프레임워크를 새로 들이지 않는다. 스타일은 static/css/site.css에만 쓴다.
확인 방법: 숨긴 콘텐츠가 목록에 없는지, 브라우저 폭을 줄였을 때 카드가 한 줄로 바뀌는지 본다.
```

### 4. 상세 페이지 `step-04`

```text
목적: 콘텐츠 하나의 상세 페이지를 만든다.
끝나는 기준: /contents/<slug>/ 에 표지, 종류, 제목, 설명, 가격, 구매 버튼이 보인다. 숨긴 콘텐츠는 404.
하지 말 것: 구매 버튼에 결제 기능을 붙이지 않는다(다음 요청에서 한다).
확인 방법: 목록에서 카드를 눌러 들어가고, 숨긴 콘텐츠의 주소를 직접 입력해 404를 본다.
```

## 판매

### 5. 회원 가입과 로그인 `step-05`

```text
목적: 가입, 로그인, 로그아웃, 비밀번호 재설정을 Django 기본 기능으로 만든다.
끝나는 기준: 가입하면 바로 로그인되고, 머리말에 아이디와 로그아웃이 보인다.
하지 말 것: 비밀번호를 직접 저장하거나 해시를 직접 만들지 않는다. 소셜 로그인은 넣지 않는다.
확인 방법: 가입, 로그아웃, 다시 로그인, 틀린 비밀번호로 로그인 순서로 눌러 본다.
```

### 6. 구매 기록 표 `step-06`

```text
목적: payments 앱을 만들고 구매 기록 표(Order)를 둔다.
끝나는 기준: 주문이 구매자와 콘텐츠를 가리키고, 금액과 상태(결제 대기, 결제 완료, 취소)를 가진다. 관리자 화면에서 주문을 본다.
하지 말 것: 콘텐츠를 지우면 주문이 함께 지워지게 하지 않는다.
확인 방법: 관리자 화면에서 주문을 하나 만들고, 그 주문의 콘텐츠를 지우려 할 때 막히는지 본다.
```

### 7. 결제 연결(테스트용) `step-07`

```text
목적: 구매 버튼에서 결제창을 거쳐 결제 완료까지 잇는다. 실제 결제 대행 서비스 대신 같은 흐름의 가상 결제 서비스(fakepg)를 쓴다.
끝나는 기준: 로그인하지 않았으면 로그인으로 보낸다. 결제창에서 돌아오면 서버가 결제 키로 다시 확인하고, 금액이 주문과 같을 때만 결제 완료로 바꾼다. 서명이 맞는 웹훅만 처리하고 같은 알림이 두 번 와도 한 번만 처리한다.
하지 말 것: 주소에 붙어 온 금액과 상태를 믿지 않는다. 카드 정보를 받는 칸을 우리 사이트에 만들지 않는다.
확인 방법: 결제 완료 주소의 amount 값을 바꿔 열면 거절되는지, 웹훅을 서명 없이 보내면 400이 나는지 본다.
```

### 8. 구매자 내려받기 `step-08`

```text
목적: 구매자가 내 자료실에서 산 콘텐츠를 내려받거나 본다.
끝나는 기준: 결제를 마친 주문의 구매자만 받는다. 내려받기 주소는 몇 분 뒤 만료된다.
하지 말 것: 판매 파일에 공개 주소를 만들지 않는다. 로그인과 결제 코드는 고치지 않는다.
확인 방법: 구매자, 구매하지 않은 회원, 로그인하지 않은 방문자로 각각 /download/<주문 번호>/ 를 열어 본다. 테스트를 돌린다.
```

## 마무리

### 9. 구매 알림 메일 `step-09`

```text
목적: 결제가 끝나면 구매자에게 구매 확인 메일을 화면과 따로 보낸다.
끝나는 기준: 결제 완료 직후 메일이 한 통 나간다. 같은 주문에 두 번 보내지 않는다. 개발 중에는 메일이 터미널에 찍힌다.
하지 말 것: 메일 서비스의 비밀번호를 코드에 적지 않는다. 결제 코드는 건드리지 않는다.
확인 방법: 테스트 결제를 하고 터미널에 찍힌 메일 내용을 읽는다.
```

### 10. 안내 문구와 오류 화면 `step-10`

```text
목적: 404, 403, 500 화면과 안내 문구를 다듬고, 운영 설정을 점검한다.
끝나는 기준: 오류 화면이 사이트 모양을 따른다. python manage.py check --deploy 경고를 읽고 운영 설정을 환경 변수로 받는다.
하지 말 것: 오류를 없애려고 보안 설정을 끄지 않는다.
확인 방법: DEBUG를 끄고 없는 주소를 열어 본다. 운영 설정으로 check --deploy를 돌린다.
```

## 첫 판 뒤에 더한 것 `book-v1`

책의 설명에 맞춰 첫 판 뒤에 더한 작은 기능들이다.

- 콘텐츠 표에 할인가(sale_price) 칸 더하기: 마이그레이션 0002
- 관리자 화면에서 판매 기록을 CSV로 내려받기
- 콘텐츠 목록을 JSON으로 주는 API(`/api/contents/`)
- 전날 판매 건수를 운영자에게 메일로 보내는 명령(`python manage.py sales_report`)
- 저장소에 올릴 때마다 테스트를 돌리는 GitHub Actions 설정
- 운영 서버용 Dockerfile
